# Contributing — миграционная политика (MVP-дружелюбная)

Цель

- Обеспечить единый и воспроизводимый поток работы со схемой БД: любой разработчик/сервер должен подниматься командой `alembic upgrade head`.
- Избежать «локальных правок в БД» и разногласий между средами (CI vs прод).

Основные правила (жёсткие, но практичные)

- **Истина схемы — Alembic**, не модели. Все изменения, влияющие на таблицы/колонки/индексы → обязательная миграция.
- **Никаких ручных правок БД**. Если правка сделана вручную — это техдолг до ближайшей миграции и должна быть задокументирована в PR.
- **Модели и Alembic должны импортироваться без запуска приложения.** (например, `models.py` и `env.py` не должны требовать запущенного сервиса)
- **Автогенерация миграций — черновик.** После `alembic revision --autogenerate` обязательно:
  - проверить diff вручную;
  - явно прописать `nullable`, `server_default`, индексы и т. п.;
  - прогнать миграцию на чистой БД и на существующей (если изменение критично для данных).

Два режима разработки

- **MVP / Dev** — допускается `docker compose down -v` и пересоздание БД при локальной разработке.
- **Prod** — дроп/фулл ресет запрещён; миграции должны быть backward compatible и не ломать имеющиеся данные/код.

Политика совместимости (sunset)

- **Runtime-проверки существования колонок** допускаются только временно и должны быть помечены комментарием:

```py
# COMPAT: remove after migration <rev_id>
if "new_column" in get_columns("table"): ...
```

- В PR укажите ревизию миграции `rev_id` (или ссылку на миграцию). После того как миграция гарантированно накатывается на прод — проверку удаляем.
- Каждая такая проверка имеет срок жизни и должна быть удалена в ближайшем релизе после миграции.

Процедура релиза

1. На staging: `alembic upgrade head` (проверить, что прошла без ошибок).
2. Деплой кода.
3. Мониторинг ошибок миграции в логах и быстрый откат/фиксы при обнаружении проблем.

Чек-лист перед merge (обязательно)

- [ ] Есть миграция для всех изменений схемы (если нужно)
- [ ] `alembic upgrade head` проходит на чистой базе (smoke покрывает это)
- [ ] Smoke-compose зелёный
- [ ] Unit tests зелёные
- [ ] Все `# COMPAT:` пометки в коде задокументированы в PR с `rev_id`

Тесты / минимальный набор (что добавить вскоре)

- Авторизация по `telegram_id` — чужой `telegram_id` не видит чужую сессию.
- Лимиты (daily/monthly/rate limit) — минимум один happy и один deny кейс.
- Тест миграций: `alembic upgrade head` (+ опционально `alembic downgrade -1`, если даунгрейды поддерживаются). Если даунгрейды не поддерживаются — зафиксировать это в политике.

Ограничения и риски

- Поддержка старой схемы через runtime checks удобна, но скрывает несоответствия; у таких проверок должна быть ограниченная продолжительность жизни.
- Downgrade миграций часто бывает сложным; для MVP можно явно заявить, что `downgrade` не гарантируется, и это должно быть отражено в PR/доках.

Предложения по автоматизации (на будущее)

- Добавить CI-check: если PR меняет модели — проверить наличие миграции (хотя бы предупреждение).
- Включить smoke-compose в CI (уже сделано) — это покрывает `alembic upgrade head` на чистой БД.

---

Спасибо — следуя этим простым правилам, мы уменьшаем техдолг и убираем «лотерею» при деплое и у пользователей.
